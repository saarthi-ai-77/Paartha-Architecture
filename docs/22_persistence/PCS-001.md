## 1. Formal Definition of Persistent Cognition (Deliverable 1)

**Persistent cognition** is the capacity of a system to maintain and evolve an internal representation of its current situation — what it is trying to do, what it currently believes, what it is watching for — across a sequence of interactions, such that later behavior is conditioned on that representation rather than solely on the immediately preceding input. It is distinguished from single-shot request processing by three properties, each independently checkable:

1. **State outlives the triggering event.** A representation written in response to interaction $t$ remains available and is not re-derived from scratch at interaction $t+1$.
2. **State evolves, not merely accumulates.** Unlike a fact store (append, rarely overwrite), persistent-cognition state is expected to be *overwritten* as understanding changes (a goal completes, a belief is revised) — the access pattern CTX-001 §4 already identified as structurally different from ordinary episodic storage.
3. **State can, in principle, be acted on without an external trigger.** A system exhibiting persistent cognition can in principle notice something (a deadline, a contradiction, a completed sub-goal) and act, not only respond to a new request. This third property is the one this document's reduction analysis (Section 3) finds is **not** yet exercised by anything validated in this program — see Section 3, Question 4/5 and Section 5.

**Epistemic status of this definition itself:** Reasoned Hypothesis. It is a working definition constructed to make the reduction analysis below checkable, not itself an empirical claim.

## 2. Computational Taxonomy: Learning, Memory, Knowledge, Governance, Cognition (Deliverable 2)

Using only genuinely-validated program vocabulary (ACA v1.0 §1–2, `docs/13_state_model/SOS-001.md`, CTX-001):

| Term | Computational referent | Distinct, or a view onto something else? |
|---|---|---|
| **Memory** | S_episodic — the substrate itself (ACA v1.0 §1.1) | Distinct — a storage mechanism, not a claim about content |
| **Knowledge** | Content in S_episodic/S_semantic that has survived consolidation and is reliably retrievable | Not distinct — a *status* of stored information (CTX-001 §2), not a separate substrate |
| **Learning** | The UPDATE calls that write to S_episodic (gated or unconditional) and the gradient steps that write to S_semantic | Not distinct — an application of an existing function (UPDATE) to existing substrates, per ARS-001 §5.5's own reduction of ME-03 to EVALUATE→SELECT→UPDATE |
| **Governance** | Per `docs/20_governance/KGP-001.md` (genuinely grounded in EXP-027/031): the audit step between a local update and its integration into global state | An honest open question, tagged Reasoned Hypothesis throughout its own source document — not re-litigated here, only noted as adjacent to but distinct from cognition |
| **Cognition (this document's referent)** | The working-state mechanism (CTX-001 §4/§10, validated by EXP-019) plus the ordinary application of EVALUATE/SELECT/UPDATE/COMPOSE to it, repeated over a sequence of interactions | **This is the central question Section 3 investigates** — is "cognition" a genuinely new computational category, or the same four functions applied to a specific kind of state (working state) under a specific temporal pattern (repeated, state-carrying)? |

**Overlap, stated precisely:** Memory (S_episodic) and the "working state" partition CTX-001/EXP-019 validated are the *same substrate class*, differing only in write discipline (gated vs. unconditional) — not two things. Learning and Governance both write to global state; Governance's entire justification (KGP-001) is that they should not be the same *step*. Cognition, as defined in Section 1, is not a fifth item alongside these four — Section 3 tests whether it is fully explained by them.

## 3. Reduction Analysis Against PCS-001's Five Questions (Deliverable 3)

### Question 1 — Are attention, goals, task progress, environmental awareness, monitoring, prediction state, and execution context reducible to existing substrates?

Reduction attempted against the same admission criterion ARS-001 §5.1 and CTX-001 §1 use throughout this program:

| Concept | Reduction attempt | Result |
|---|---|---|
| Current attention / execution context | A small set of continuously-overwritten fields | **Reduces** — this is exactly what EXP-019 validated (a reserved S_episodic partition, unconditional write). Not a new concept; the same mechanism CTX-001 already tested, applied to different field names. |
| Active goals / task progress | Same shape as "current topic," EXP-019's tested case | **Reduces**, by direct structural analogy — untested for goal-specific content specifically, but nothing about "goal" content differs in kind from "topic" content in EXP-019's design. |
| Monitoring responsibilities | "Is condition X still true" repeatedly checked | **Reduces** to EVALUATE applied to a threshold value stored in working state, re-evaluated on each new event. |
| Prediction state | A candidate future value, later compared to what actually happens | **Reduces** to COMPOSE (generate the candidate) + working-state storage (EXP-019) + EVALUATE (compare prediction to outcome once known) — exactly EVALUATE's existing signature, `(Representation, Reference) → Score`. |
| Environmental awareness | Perceiving something *not* triggered by a user request | **Does not fully reduce as a storage question** — the *content* reduces to working state like everything else, but the *trigger* does not: every validated experiment in this program (including SIP-001/SIP-002) is triggered by an incoming request. Nothing has been tested with a non-request-triggered ingress event. This is a genuine, narrow gap, isolated to **triggering**, not to representation — see Section 5. |

**Conclusion for Question 1:** six of seven named concepts reduce cleanly to EXP-019's already-validated working-state mechanism. The seventh (environmental awareness) reduces on the *representation* side but exposes a real gap on the *triggering* side, addressed in Section 5, not smoothed into the others.

### Question 2 — Does continuous cognition require persistent state independent of prompt reconstruction, or is this an implementation optimization?

This is not a new question — CTX-001 §6 already investigated it under a different name ("Token History vs. Structured Cognitive State") and reached a conclusion this document adopts rather than re-derives: structured, persistent state is very likely the *right kind of object*, by direct analogy to EXP-001's validated finding that bounded, curated retention beats raw hoarding under a fixed budget. EXP-019 then made this concrete and validated it for context specifically. **The false binary in the question as posed:** "implementation optimization" vs. "fundamentally different computational requirement" are not the only options. The correct characterization, per already-validated evidence: persistent state is a **fundamentally different data structure** (validated — EXP-019) governed by a **retention/update policy that remains genuinely unsolved** (EXP-018/010's negative result for the *ordinary fact* case; untested for working-state content specifically, since EXP-019's task never ran long enough to stress the retention policy the way EXP-018 did). Neither answer PCS-001 poses is exactly right; the honest one is narrower and already partly evidenced.

### Question 3 — What computational object propagates between reasoning cycles: knowledge, or something richer?

Applying the reduction directly: beliefs = EVALUATE-LOCAL's confidence score attached to a working-state entry (already a first-class quantity, not new). Objectives / commitments = working-state fields (EXP-019). Execution plans = a COMPOSE output over a sequence — this is RC-04 (planning), which ARS-001 §1.4 already identified as **the one item in its own cluster that does not fully reduce**, and which ACA v1.0 §8 already states is unimplemented. Uncertainty estimates = EVALUATE's score output, already first-class. Environmental models = ordinary S_episodic/S_semantic content, at whatever granularity is warranted, no new substrate implied.

**Conclusion:** what propagates is not a genuinely new kind of object. It is a bundle of (working-state fields, EVALUATE scores, ordinary substrate content) that *looks* richer than "knowledge" only because several already-distinct quantities are being observed together. The one piece that doesn't reduce (planning/RC-04) is not new — it is the same gap ARS-001 named at the very beginning of this program's architecture work, now recurring under a different name.

### Question 4 — Is cognition better modeled as state evolution than request processing?

Given Question 2's answer (persistent working state is real and validated), this is already how the system that has been validated is shaped: SIP-001/SIP-002's own pipeline (`docs/14_integration/SIP-001.md` §3, §6) is *already* Context Resolution (read state) → dispatch → compute → **Response** → **Episode Creation / Experience Storage** (write state) — a state-transition shape, not a stateless function call, for every request already tested. "Reasoning becomes one transition within a larger process instead of the central mechanism" is not a new requirement to satisfy — it is a description of what the already-validated pipeline does. Routing/dispatch in SIP-001 is already exactly one stage among several, not privileged over the others.

### Question 5 — Is the Perception → State Update → Goal Evaluation → Planning → Reasoning → Action → Environment Change loop reducible to existing primitives?

Mapping each stage against the four validated functions:

| Loop stage | Reduction |
|---|---|
| Perception | An ingress event — reduces to a *new event source* feeding the existing pipeline (Question 1's "environmental awareness" gap: representation reduces, triggering does not) |
| State Update | UPDATE — existing, validated (EXP-001, EXP-019) |
| Goal Evaluation | EVALUATE — existing, validated (EXP-009), applied to a working-state goal field |
| Planning | COMPOSE, generating candidate action sequences — this is RC-04, **already flagged as the one non-fully-reducible piece since ARS-001 (§1.4)**, still untested (EXP-014, not run). Not a new finding. |
| Reasoning (selection) | SELECT — existing, validated (EXP-003, EXP-021) |
| Action | Response output — existing, trivial engineering |
| Environment Change | External to ACA by construction — not a computational claim about ACA at all |

**Conclusion:** the entire proposed loop maps onto the four already-existing functions, applied repeatedly, with exactly one already-known gap (RC-04/planning) and one already-identified-in-this-document gap (non-request-triggered ingress). Neither is a "fifth function" or a new substrate.

## 4. Attempted Falsification of the Central Question (Deliverable 3, Continued)

**Claim under test, per the directive's own framing:** "ACA has reached the boundary of architectures that explain learning and requires a second layer of computational theory to explain continuous cognition."

**Attempted falsification of the strong version:** if this were true, Section 3's reduction attempts should have failed broadly — most of the five questions should have exposed genuinely new computational categories. They did not. Six of seven Question-1 concepts, all of Question 3's candidates but one, and six of Question 5's seven loop stages reduce cleanly to combinations already validated or already on record as open (RC-04) before this document existed. **The strong version of the claim is not supported by this analysis and is rejected**, in the same spirit CTX-001 §5 rejected the strong version of "cognitive state is ACA's primary object" — an appealing framing that does not survive the reduction it was subjected to.

**What survives, precisely, not smoothed into the rejected strong claim:**
1. **RC-04 (planning)** — not new to this document; ARS-001 named it in the very first reduction pass and it remains untested (EXP-014).
2. **Non-request-triggered ingress ("environmental awareness" / autonomous operation)** — this *is* newly precise here. Every experiment this program has run, including the two integrated runtimes (SIP-001, SIP-002), only ever acts in response to an incoming request. Nothing has tested a system doing anything absent an external trigger — noticing, monitoring, or acting on a self-generated impulse. This is not "persistent cognition needs a new function" — Section 3 showed the *representation* side reduces fine — it is a **scheduling/orchestration gap**, the same *kind* of gap CTX-001 §3 already named once (there, "Gap Curriculum Generation," a missing scheduled timescale, not a missing function).

**Answer to PCS-001's own stated success criterion:** per the directive's own terms ("a successful outcome may conclude either: ACA already contains sufficient mechanisms... or persistent cognition represents a computationally distinct problem... both are scientifically acceptable") — **this document concludes the former, with two named, precisely-scoped, already-partially-known exceptions, neither of which requires new architectural theory.** Both exceptions require dedicated engineering/scheduling work and, for RC-04 specifically, a falsification experiment already on the roadmap (EXP-014) — not conceptual invention.

## 5. Missing Computational Capability, Precisely Scoped (Deliverable 4)

Not "persistent cognition as a category" — that reduces. Two specific, narrow gaps:

1. **RC-04 / planning** — already named, already on the roadmap, still untested. No new work is proposed here beyond what already exists (EXP-014).
2. **Self-triggered / event-driven ingress** — genuinely not exercised by anything validated. Every pipeline this program has built (`runtime/sip001/`, `runtime/sip002/`) is a function of an incoming request; none has ever run a step without one. This is an **orchestration gap** (where does a non-request event come from, and what triggers the pipeline to run against it), not a missing function — EVALUATE/SELECT/UPDATE/COMPOSE do not need to change; something needs to call them without a request present.

## 6. Falsification Plan for the One Genuinely New Gap (Deliverable 5) — Proposed, Not Executed

Per DEC-006, this is a *plan*, not a result. The gap named in Section 5.2 is the only one this document treats as requiring new empirical work rather than an already-scheduled experiment.

**Proposed EXP-032 (not run): Self-Triggered Ingress Under No External Request.**
- **Reproducible runtime observation to seek:** extend `runtime/sip001/` or `runtime/sip002/` with a scheduler that periodically checks working-state fields (e.g., a stored "deadline" or "monitored condition") and, absent any new user request, decides whether to act (write a new episode, change a working-state field, or emit output) based solely on EVALUATE applied to existing state.
- **Isolation of the responsible variable:** compare against a control where the same condition is only checked when a request happens to arrive (today's behavior) — does self-triggering change anything measurable, or does it turn out that request-triggered checking, sufficiently frequent, is behaviorally indistinguishable (in which case the "gap" dissolves into a scheduling-frequency question, not a architectural one)?
- **What would constitute a genuine finding:** if self-triggered and request-triggered checking are behaviorally indistinguishable under reasonable request frequency, the gap in Section 5.2 reduces further — to "make sure the orchestration loop runs often enough," an engineering parameter, not new theory. If they diverge meaningfully (e.g., a monitored deadline is missed under request-triggered-only checking because no request happens to arrive in time), that is a real, demonstrated necessity — and only then, per DEC-006 Step 4, would a scheduling mechanism be proposable as an architectural addition — still not a new function or substrate, just an orchestration change to *when* the existing functions run.
