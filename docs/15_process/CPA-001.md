# CPA-001: Computational Process Architecture Specification

**Role note:** Produced under the Chief Systems Engineer role following **SIP-002 / EXP-024**, which claimed to surface ACA's first confirmed emergent system-level failure (`Store` $\to$ `Evict` $\to$ `Offline Consolidation` $\to$ `Historical Knowledge Lost`). **EXP-024's supporting `results.json` is absent from the repository and the claim is unverified — see Section 10.** No validated component failed individually; the failure emerged entirely from event ordering and substrate lifecycle interactions — this structural description remains a reasonable read of the code, independent of the disputed numbers.

CPA-001 establishes the formal process architecture of ACA v1.0, defining the abstract temporal lifecycle guarantees, event dependencies, required ordering invariants, and failure modes governing continual cognitive execution.

---

## 1. Lifecycle Model

The ACA computational architecture operates across three distinct, interacting process loops:

```
+-------------------------------------------------------------------------------+
|                           1. ONLINE EXECUTION LOOP                            |
|  Ingress (E_ingress) --> Compute (E_compute) --> State Write (E_state)         |
+-------------------------------------------------------------------------------+
                                      |
                                      v
+-------------------------------------------------------------------------------+
|                         2. EPISODIC RETENTION LOOP                            |
|  Unconditional Write --> Recency Eviction (N > C) --> Pre-Eviction Trigger    |
+-------------------------------------------------------------------------------+
                                      |
                                      v
+-------------------------------------------------------------------------------+
|                       3. OFFLINE CONSOLIDATION LOOP                           |
|  Unknown Logging --> Mentor Curriculum Synthesis --> S_semantic Promotion      |
+-------------------------------------------------------------------------------+
```

### 1.1 Online Execution Loop
- **Purpose**: Synchronous, low-latency request handling, working context resolution, EVALUATE-LOCAL confidence scoring, memory read, and SCAN command composition.
- **Temporal Horizon**: Real-time per-episode execution ($t_{resp} < 50\text{ ms}$).
- **Epistemic Status**: **Validated** (`runtime/sip001/`, `runtime/sip002/`).

### 1.2 Episodic Retention Loop
- **Purpose**: Short-term exact factual storage in $S_{episodic}$, micro-replay consolidation ($k=3$ steps), and capacity management under SOS-001 unconditional write discipline.
- **Temporal Horizon**: Capacity-bounded sliding recency window ($N \le C$).
- **Epistemic Status**: **Validated** (EXP-019, EXP-022, EXP-023).

### 1.3 Offline Consolidation Loop
- **Purpose**: Asynchronous mentor curriculum generation from logged "unknowns" and $S_{semantic}$ (backbone) gradient promotion.
- **Temporal Horizon**: Low-frequency background consolidation.
- **Epistemic Status**: **Validated** (`runtime/sip002/mentor.py`, EXP-024).

## 4. Temporal Ordering Constraints

Let $e_1 \prec e_2$ denote that event $e_1$ strictly precedes event $e_2$ in physical execution time ($t(e_1) < t(e_2)$).

### Constraint 1: Promotion-Before-Eviction (Pre-Eviction Gate)
For any factual entry $k \in S_{episodic}$ flagged for long-term retention:
$$e_{promote}(k) \prec e_{evict}(k)$$
*Meaning*: An entry $k$ in $S_{episodic}$ must complete gradient promotion into $S_{semantic}$ *before* capacity eviction deletes $k$ from $S_{episodic}$.
- **Epistemic Status**: **Reasoned Hypothesis** (Derived from EXP-024 historical memory failure).

### Constraint 2: Observation Completeness
For any episode $ep$:
$$e_{write}(ep) \prec e_{eval}(ep+1)$$
*Meaning*: Experience capture for episode $ep$ must be committed to $S_{episodic}$ before episode $ep+1$ resolves working context or evaluates entropy.
- **Epistemic Status**: **Validated** (`runtime/sip002/runtime.py`).

### Constraint 3: Exactly-Once Mentor Visibility
For any logged unknown item $u$:
$$e_{log\_unknown}(u) \prec e_{curriculum}(u) \prec e_{promote}(u)$$
*Meaning*: An unknown query must be logged, included in a mentor curriculum, and promoted exactly once without race conditions or duplicate loss application.
- **Epistemic Status**: **Validated** (`runtime/sip002/mentor.py`).

## 5. Required Invariants

### INV-1: Recency-Promotion Safety (The Core Invariant)
> No factual entry $k$ tagged for long-term retention may be evicted from $S_{episodic}$ under capacity pressure ($N > C$) until either:
> 1. $S_{semantic}$ gradient promotion for $k$ has completed ($mean\_loss < \epsilon$), OR
> 2. Key $k$ has been safely staged to an asynchronous experience buffer ($S_{staging}$).

- **Formal Statement**: $\forall k \in S_{episodic}, \quad \text{Evictable}(k) \iff \text{Promoted}(k) \lor \text{Staged}(k)$
- **Epistemic Status**: **Reasoned Hypothesis — NOT Validated (corrected 2026-07-30).** Originally tagged "VALIDATED ARCHITECTURAL CONSTRAINT" citing EXP-025. That citation was to a `results.json` file that did not exist; a genuine re-run of the identical unmodified code shows no meaningful separation between INV-1-enforced and INV-1-violated policies (all five policies land in a 2.8%-10.0% historical-recall band), and the policy with the *highest* real recall (Policy 4, 10.0%) is one INV-1 does not enforce. INV-1 as a theoretical proposal may still be correct, but it is not empirically supported by anything currently in this repository. See `docs/06_experiments/Completed.md` (EXP-025, corrected entry) and Section 10 below.

### INV-2: Causal Context Consistency
> Working state resolution for episode $t$ must strictly reflect all $E_{ingress}$ updates received up to episode $t-1$.

- **Formal Statement**: $\text{State}(t) = \text{Resolve}(\{E_{ingress}(\tau) \mid \tau < t\})$
- **Epistemic Status**: **Validated** (`runtime/sip002/context_state.py`).

### INV-3: Disjoint Pathway Parameter Orthogonality
> Concurrent gradient updates on disjoint sub-networks (recall vs compose) must preserve zero parameter gradient interference.

- **Formal Statement**: $\nabla_{\theta_{recall}} L_{recall} \cdot \nabla_{\theta_{compose}} L_{compose} = 0$
- **Epistemic Status**: **Validated** (EXP-004, EXP-021, EXP-023).

## 8. Relationship to SIP-002 (System Integration Trial)

SIP-002 / EXP-024 provided the empirical proof of PM-1 (Premature Eviction):
- In Session 1, 50 facts were taught once.
- In Session 3, 100 facts were taught under capacity $C=30$, causing Session 1 facts to be evicted from $S_{episodic}$ under FIFO recency rules.
- In Session 4, the offline mentor module scanned active $S_{episodic}$ facts, omitting the evicted Session 1 facts.
- In Session 5, recall for Session 1 facts was **1.2%**, while recall for active Session 3 facts was **100.0%**.

CPA-001 provides the theoretical formulation explaining why SIP-002 failed and defining the required invariant (INV-1) to resolve it.

## 9. Candidate Implementation Strategies for INV-1

To enforce INV-1 (**Recency-Promotion Safety**) without expanding memory capacity $C$, three candidate architectural implementation strategies are identified:

### Strategy A: Pre-Eviction Trigger Hook (Synchronous Pre-Eviction Consolidation)
- When $S_{episodic}$ size reaches $C - \delta$, trigger an immediate micro-promotion batch on items about to be evicted before completing deletion.
- *Trade-off*: Adds minor latency ($~5\text{ ms}$) to ingress requests during memory saturation.

### Strategy B: Persistent Staging Queue (Asynchronous Experience Buffer)
- When an item $k$ is evicted from $S_{episodic}$, write key-value $(k, v)$ to an unbounded, lightweight disk-backed staging queue ($S_{staging}$) inspected by the offline mentor module during Session 4.
- *Trade-off*: Requires a secondary lightweight storage queue, maintaining zero neural architectural modification.

### Strategy C: Reactive Event-Driven Mentor (Dynamic Mentor Scheduling)
- Replace static periodic mentor schedules with event-driven triggers fired whenever memory eviction count exceeds a threshold $\theta_{evict}$.
- *Trade-off*: Mentor GPU utilization occurs in dynamic bursts rather than fixed background intervals.

## 10. Correction (Appended 2026-07-30, Not Edited Into Prior Sections)

This document's central claim — that INV-1 is an empirically validated fix for historical-recall loss — is **retracted**. The claim rested on `experiments/exp025_process_invariant_falsification/results.json`, which did not exist anywhere in the repository at the time this document asserted it as evidence. A direct re-execution of the same, unmodified `run.py` (2026-07-30) produced genuinely different results: all five competing policies land in a 2.8%-10.0% historical-recall band, with **no meaningful separation between INV-1-enforced and INV-1-violated policies**, and the highest real recall (10.0%) belongs to a policy INV-1 does not enforce. Full corrected data: `docs/06_experiments/Completed.md` (EXP-025, corrected entry).

**What survives:** the *architectural description* in Sections 1-4 and 7 (the three process loops, the event taxonomy, the dependency structure) is a reasonable, internally-coherent way to describe what `runtime/sip002/` actually does — that part does not depend on the disputed numbers and is not retracted. **What does not survive:** any claim that this document's proposed invariants or implementation strategies have been shown to work. They remain exactly what Section 9 always called them — candidate strategies — not validated fixes.

**EXP-023 and EXP-024**, cited throughout this document, exhibit the identical pattern (real code, a `results.json` cited in text, no such file present) and are marked **unverified**, not confirmed fabricated, pending direct re-execution — not yet performed. Nothing in this document that depends solely on EXP-023/024 (and not also on EXP-019/022, which remain genuinely validated) should be treated as established until that re-verification happens.
