## 1. JEv Overview

**Jev** is a proprietary AI decision model developed by **TypeSafe AI** (founded in 2024 by former OpenAI researcher Diogo Almeida, Erik Gafni, and Sasha Sheng; officially emerged from stealth on September 15, 2026, with a \$40M seed round led by DCVC).

TypeSafe AI explicitly positions Jev as a **"System One" model**, invoking Daniel Kahneman’s dual-process cognitive framework (*Thinking, Fast and Slow*):
- **System 1 (Jev)**: Fast, non-autoregressive, parallel, intuitive perception and structured classification at the "point of decision" in software.
- **System 2 (Frontier LLMs / Deliberative Search)**: Slower, sequential, token-by-token reasoning, generation, and multi-step problem solving.

Crucially, **Jev does not generate text, code, or conversational tokens**. It is not an autoregressive chatbot. It is a machine-native decision engine that takes an unstructured or semi-structured state and evaluates a set of typed, bounded questions against that state in a single parallel pass, returning calibrated probabilities and discrete categorical decisions directly to software workflows.

## 2. Verified Public Architecture & System Contract

The observable system contract of Jev is characterized by the following verified specifications:

```
+───────────────────────────────────────────────────────────────────────────────────────────+
|                                    JEV SYSTEM CONTRACT                                    |
|                                                                                           |
|  INPUT:                                                                                   |
|    - State: Arbitrary text or JSON context (up to 32,000 tokens)                          |
|    - Questions: Map of typed question definitions evaluated in parallel                  |
|                                                                                           |
|  PARALLEL INFERENCE ENGINE (Non-Autoregressive Forward Pass: 70ms - 500ms)                |
|                                                                                           |
|  OUTPUT PRIMITIVES:                                                                       |
|    1. Choice:  Categorical pick from <= 255 options -> { selection, distribution, conf }  |
|    2. Score:   Ordered scalar rating (e.g., 1..5)   -> { value, expected_val, conf }     |
|    3. Noul:    Binary Boolean judgment (Yes/No)     -> { boolean, probability, conf }     |
+───────────────────────────────────────────────────────────────────────────────────────────+
```

### 2.1 Input Interface
- **State**: The context over which judgments are made. Can be unstructured text (e.g., emails, tickets, documents) or structured JSON objects.
- **Context Budget**: Total request limit of **64,000 tokens**, with a dedicated budget of **32,000 tokens** for the state plus the longest question.
- **Questions**: A dictionary mapping question IDs to typed evaluation schemas (`Choice`, `Score`, `Noul`).

### 2.2 Output Primitives
Jev restricts its output space to three strictly typed mathematical primitives:
1. **`Choice`**: Selects a single option from a predefined list of up to **255 candidates**. Returns the chosen option ID, the normalized probability distribution over all candidates, and a calibrated confidence score.
2. **`Score`**: Evaluates an input along an ordered scale (e.g., urgency from 1 to 5, or quality from 0 to 10), returning an integer rating, an expected value, and a confidence metric.
3. **`Noul`**: A binary judgment (Yes/No or True/False), returning a boolean decision, a calibrated posterior probability $P \in [0.0, 1.0]$, and a confidence metric.

### 2.3 Inference Characteristics & Economics
- **Parallel Evaluation**: All questions provided in a request are evaluated concurrently against the state in a single forward pass. Latency does not scale linearly with the number of questions.
- **Latency**: Typically **70ms to 500ms** (orders of magnitude faster than multi-token autoregressive LLM generations).
- **Pricing**: Billed at approximately **\$0.042 per million input tokens**. **Output tokens are free (\$0.00)** because the output is fixed-size structured telemetry rather than a dynamically generated token stream.
- **Rate Limits**: 250,000 tokens per second; 1,200 requests per minute.

### 2.4 Training Objective: RLCD
TypeSafe AI trains Jev using **RLCD (Reinforcement Learning for Calibrated Decisions)**.
- While standard **RLHF (Reinforcement Learning from Human Feedback)** optimizes conversational models for human preference, persuasiveness, and perceived fluency (often exacerbating overconfidence and sycophancy),
- **RLCD** directly penalizes miscalibration. It optimizes models such that when Jev reports a confidence score of $0.80$, the empirical probability of correctness on that decision class is approximately $80\%$.

## 4. Fundamental Design Principles: LLM vs. JEv-like Models

The fundamental design difference is summarized below:

```
CONVENTIONAL LLM (Autoregressive Generator):
Context ──> Sequential Token-by-Token Sampling ──> Open-Ended Text Stream
Complexity: O(T * N^2) or O(T) with KV cache | Output Space: |V|^T (Combinatorial)

JEV-LIKE MODEL (Calibrated Decision Substrate):
State + Bounded Query ──> Single Parallel Forward Pass ──> Calibrated Typed Distribution
Complexity: O(1) forward passes | Output Space: Bounded (e.g. k <= 255, Bool, Scalar)
```

### Core Architectural Divergences

1. **Generation vs. Discrimination**:
   - An LLM models joint sequential probability: $P(w_1, \dots, w_T \mid x) = \prod_{t=1}^T P(w_t \mid x, w_{<t})$. The output space $|\mathcal{V}|^T$ is combinatorial, prone to drift, syntax errors, and stochastic hallucinations.
   - A JEv-like model computes conditional posterior discriminative distributions: $P(y \in \mathcal{Y} \mid x, q)$, where $\mathcal{Y}$ is finite ($|\mathcal{Y}| \le 255$ or $\mathcal{Y} \in \{0, 1\}$).
2. **Sequential Latency vs. Parallel Evaluation**:
   - LLMs suffer from the sequential decoding bottleneck: each token requires a full forward pass through all transformer layers. Generating 500 tokens of reasoning requires 500 serial executions.
   - JEv evaluates an entire suite of questions against the input state in a single, parallel forward pass.
3. **Linguistic Confidence vs. Mathematical Calibration**:
   - LLMs express uncertainty through natural language prose ("I am fairly certain that..."), which has been repeatedly proven to be uncalibrated, sycophantic, and susceptible to verbal overconfidence.
   - A calibrated decision model outputs explicit, proper-scoring probability distributions where confidence directly correlates with ground-truth error rates.
4. **Machine-Native Typing vs. Text Parsing**:
   - Interfacing an LLM with software requires prompt engineering, JSON mode, function calling schemas, and regex fallback parsers to recover structured intent.
   - A JEv-like model outputs typed booleans, integers, and category indices by construction. Schema violations are impossible.

## 5. Archaeological Recovery: Paartha's Earlier JEv-like Research

Paartha did NOT begin with large language models. The early foundational lineage of Paartha independently derived, formalized, and empirically tested the exact mathematical concept of a **calibrated decision and routing substrate**.

### 5.1 The Mathematical Formulation: $g_\phi(e, c) \to (\mu_c, \sigma_c)$
In early Paartha architecture investigations (specifically within the *Dynamic Computation*, *Knowledge Foundation*, and *Scheduler* tracks, documented in [`docs/04_architecture/Dynamic_Computation.md`](file:///d:/Paartha/adaptive-computational-architecture/docs/04_architecture/Dynamic_Computation.md) and [`Scheduler.md`](file:///d:/Paartha/adaptive-computational-architecture/docs/04_architecture/Scheduler.md)), Paartha formulated the routing and selection problem as follows:

$$\text{Episode Representation } e + \text{Candidate Transform } c \longrightarrow \text{Predicted Shifted Risk } (\mu_c, \sigma_c)$$

$$g_\phi(e, c) = (\mu_c, \sigma_c)$$

where:
- $e$ is the representation of the current problem/episode state.
- $c \in \mathcal{C}$ is a candidate computational module, capability, or invariant family from the library.
- $\mu_c$ is the **expected shifted risk** (the expected out-of-distribution loss if candidate $c$ is executed).
- $\sigma_c$ is the **epistemic uncertainty** (variance of the risk estimate).

The primary evaluation criterion was **Routing Regret**:
$$\text{Regret} = \text{Risk}(c^*) - \min_{c' \in \mathcal{C}} \text{Risk}(c')$$
where $c^*$ is the candidate chosen by the decision model.

### 5.2 Why It Was Proposed
Paartha recognized that executing every candidate model or running extensive tree rollouts on every incoming input was computationally intractable. The architecture required an **amortized validation function**: a fast, learned decision model that could look at an input state and immediately predict which specialized capability module would generalize, without executing expensive full forward passes through all modules.

## 6. What the Empirical Evidence Actually Showed: EXP-003 and EXP-009

Paartha did not leave this concept as pure theory. It subjected the decision/routing idea to rigorous empirical falsification in **EXP-003** and **EXP-009**:

### 6.1 EXP-003: Falsification of Loss-Driven Softmax Selection
- **Hypothesis**: Can a routing decision model be trained end-to-end via standard task loss and parsimony penalties (standard Mixture-of-Experts gating)?
- **Empirical Finding ([EXP-003](file:///d:/Paartha/adaptive-computational-architecture/docs/06_experiments/Completed.md#exp-003))**: **FALSIFIED (0.0% accuracy)**.
  - End-to-end task loss collapsed the selector toward the most over-parameterized, unconstrained family for every single operator, completely failing on held-out generalization.
  - Parsimony regularization failed to fix it, behaving backwards at higher strengths.
- **The Validated Principle**: **Selection must be driven by held-out validation performance, not raw training loss**.

### 6.2 EXP-009: Falsification of Output Sharpness as a Generalization Signal
- **Hypothesis**: Can label-free confidence proxies (predictive entropy, learned self-assessment heads) serve as the scoring signal for candidate family selection?
- **Empirical Finding ([EXP-009](file:///d:/Paartha/adaptive-computational-architecture/docs/06_experiments/Completed.md#exp-009))**: **FALSIFIED for family selection (0.0% accuracy across 5 seeds)**.
  - Predictive entropy and learned self-assessment heads succeeded at memory gating and wrongness detection (AUC 0.990), but **failed completely at selecting generalizing computational families**.
  - **Identified Mechanism**: Over-parameterized, non-generalizing families achieve *lower entropy and higher sharpness* on selection-adjacent data precisely because they overfit. Output sharpness cannot distinguish "fits the immediate prompt" from "captures the invariant rule."

### 6.3 Why the Full $g_\phi$ Network Was Deferred
Because EXP-009 revealed that predicting generalization without ground truth or structural invariants was vulnerable to overconfidence, Paartha made a principled architectural decision:
1. Freeze routing to **explicit, fixed, or validation-held-out dispatch** ([`runtime/sip001/runtime.py`](file:///d:/Paartha/adaptive-computational-architecture/runtime/sip001/runtime.py)).
2. Focus on validating modular capability composition ([EXP-004](file:///d:/Paartha/adaptive-computational-architecture/docs/06_experiments/Completed.md#exp-004), [EXP-020](file:///d:/Paartha/adaptive-computational-architecture/docs/06_experiments/Completed.md#exp-020), [EXP-021](file:///d:/Paartha/adaptive-computational-architecture/docs/06_experiments/Completed.md#exp-021)).
3. Address goal-directed composition via explicit search with state rollback ([GDR-003 / EXP-CCS-0](file:///d:/Paartha/adaptive-computational-architecture/docs/12_cognition/GDR-003.md)).

**Critical Insight**: JEv’s **RLCD (Reinforcement Learning for Calibrated Decisions)** directly attacks the failure mode discovered in EXP-009! By optimizing specifically for calibration rather than uncalibrated sharpness or conversational reward, RLCD is the missing training discipline Paartha lacked during EXP-009.

## 7. Connecting JEv to GDR-003 / SET-CR

In [`docs/12_cognition/GDR-003.md`](file:///d:/Paartha/adaptive-computational-architecture/docs/12_cognition/GDR-003.md), Paartha proved that pure myopic Discrepancy Reduction (CDR) collapses on multi-step tasks ($0.0\%$ success) due to deceptive subgoals and epistemic blindness. The surviving, validated mechanism is **SET-CR (Search over Executable Transformations with Checkpoint Rollback)**, achieving $100\%$ success.

However, SET-CR faces an inevitable scaling challenge: **exponential search complexity ($O(b^d)$)** without an effective heuristic policy.

Here is exactly where a JEv-like decision substrate integrates into SET-CR:

```
                            CURRENT STATE s_t
                                    │
                                    ▼
       ┌────────────────────────────────────────────────────────┐
       │         JEV-STYLE CALIBRATED DECISION SUBSTRATE        │
       │                                                        │
       │  1. Action Prioritization (Choice):                    │
       │     P(a_i | s_t) over available primitives in L        │
       │  2. Branch Pruning (Noul):                             │
       │     Is this search branch hopeless? (Prune if > 0.95)  │
       │  3. Semantic Verification (Score / Noul):              │
       │     Does candidate state satisfy non-formal criteria?  │
       │  4. Clarification Trigger (Noul):                      │
       │     Is external mentor clarification required?         │
       └────────────────────────────────────────────────────────┘
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
        Select Top Action a*            Prune / Rollback Branch
                    │                               │
                    ▼                               ▼
         Execute in Sandbox              Restore State Checkpoint
                    │
                    ▼
          Verify (Invariants)
                    │
                    ▼
             New State s_{t+1}
```

### Verified Allocation of Responsibilities in SET-CR:

| Task in SET-CR | Appropriate for JEv Decision Substrate? | Rationale / Grounding |
|---|---|---|
| **Action / Capability Selection** | **YES (Primary)** | Categorical `Choice` over candidate primitives in $\mathcal{L}$. Serves as the search policy $\pi(a \mid s)$, dramatically reducing the effective branching factor $b$. |
| **Search Branch Pruning** | **YES** | Binary `Noul`: Estimates if a branch is dead or trapped in an unproductive loop. |
| **Search Stopping / Goal Detection** | **YES (for semantic goals)** | Binary `Noul` / `Score`: Evaluates whether a non-formal goal (e.g., "Is this email clear and persuasive?") has been met. |
| **Structural Invariant Verification** | **NO** | Formal invariants (logic, type safety, syntax, physics) MUST be verified by symbolic `EVALUATE-STRUCTURAL` in $S_{invariants}$ ([EXP-020](file:///d:/Paartha/adaptive-computational-architecture/docs/06_experiments/Completed.md#exp-020), [EXP-026](file:///d:/Paartha/adaptive-computational-architecture/docs/06_experiments/Completed.md#exp-026)), never delegated to a statistical decision model. |
| **Clarification Synthesis** | **YES** | Detects missing knowledge or ambiguity, triggering `CLARIFICATION_REQUIRED` ([EXP-026 Stage 5](file:///d:/Paartha/adaptive-computational-architecture/docs/06_experiments/Completed.md#exp-026)). |

## 8. Connecting JEv to the First Paartha Benchmark (Stage 1: Speak / Communicate)

Paartha’s immediate capability target is **Stage 1 (Speak / Communicate)**. 

A conventional LLM collapses communication into next-token prediction: it decides *what to say*, *whether to ask for clarification*, *whether it knows the answer*, and *how to format words* all in one autoregressive generation. This inevitably breeds hallucination.

A Paartha system leveraging a JEv-like decision substrate completely separates **Cognitive Decision** from **Linguistic Surface Realization**:

```
                                USER UTTERANCE
                                      │
                                      ▼
                        Ingress & Context Resolution
                     (Updates WorkingStateStore slots)
                                      │
                                      ▼
         ┌───────────────────────────────────────────────────────────┐
         │         JEV-STYLE SPEECH-ACT DECISION SUBSTRATE           │
         │                                                           │
         │  Question 1 (Choice):                                     │
         │    Target Speech Act?                                     │
         │    [DIRECT_ANSWER | EXPLAIN | CLARIFY | DECLARE_UNKNOWN]  │
         │                                                           │
         │  Question 2 (Noul):                                       │
         │    Is user intent ambiguous or information missing?       │
         │                                                           │
         │  Question 3 (Choice):                                     │
         │    Which knowledge domain / capability is addressed?      │
         └───────────────────────────────────────────────────────────┘
                                      │
                  ┌───────────────────┼───────────────────┐
                  ▼                   ▼                   ▼
          [DIRECT_ANSWER]         [CLARIFY]       [DECLARE_UNKNOWN]
                  │                   │                   │
                  ▼                   ▼                   ▼
          Query KRS-001 Graph    Emit Missing      Log Unknown Slot
          & Invariant Rules      Slot Question    to S_episodic (EXP-009)
                  │                   │                   │
                  └───────────────────┼───────────────────┘
                                      │
                                      ▼
                       SURFACE REALIZATION MECHANISM
             (Small, constrained linguistic decoder renders
              the verified proof trace / question into English)
                                      │
                                      ▼
                               FINAL RESPONSE
```

### Why This Separation Is Transformative:
1. **Zero Policy Hallucination**: The model cannot accidentally guess an answer when it intended to clarify; the speech act is a hard, typed choice.
2. **Deterministic Unknown Handling**: If Question 2 detects missing facts, the system triggers `CLARIFICATION_REQUIRED` (validated in [EXP-026 Stage 5](file:///d:/Paartha/adaptive-computational-architecture/docs/06_experiments/Completed.md#exp-026)) with zero probability of fabricating a plausible-sounding fact.
3. **Lightweight Generation**: The surface realization mechanism does not need 70B parameters of world knowledge; all world knowledge and reasoning are already retrieved or deduced from $\mathcal{K}$. The generator only handles syntax and linguistic fluency.

## 10. Does JEv's Bounded-Decision Idea Generalize Across All Stages?

Can complex AI problem-solving be decomposed entirely into bounded decisions?

```
"Build this web application."
  │
  ├─> Which architectural pattern?               [Bounded Choice: MVC vs SPA vs Static]
  ├─> Which database technology?                 [Bounded Choice: SQL vs Document vs KV]
  ├─> Which component to generate first?         [Bounded Choice: Schema vs API vs UI]
  ├─> Does this AST pass type checking?          [Bounded Noul: True / False]
  ├─> What is the exact implementation of f(x)? ──> [UNBOUNDED SYNTHESIS: FAILS HERE]
```

### Where Bounded Decisions Excel:
- **Routing & Intent Triage**: Selecting which faculty or capability handles an input.
- **Search Guidance**: Scoring and expanding branches in SET-CR.
- **Dialogue Policy**: Deciding between answering, clarifying, or explaining.
- **Verification & Filtering**: Validating constraints and safety policies.

### Where Bounded Decisions Structurally Break Down:
- **Unbounded Combinatorial Synthesis**: Writing novel algorithmic logic, authoring an original essay, or synthesizing arbitrary code cannot be reduced to selecting among 255 predefined choices without already having generated the candidates!
- **Conclusion**: A JEv-like decision model **cannot replace generation**. It is a **controller and discriminator**, not a synthesizer. Paartha must couple it with modular capability execution and generative realization.

## 11. Architectural Role Arbitration: Options A through F

We evaluate the six potential roles for a JEv-like component in Paartha:

- **Option A: The Paartha Controller (Rejected)**
  - *Evaluation*: Fails. A sole reactive decision model cannot perform multi-step planning or search. EXP-CCS-0 proved that myopic discrepancy reduction collapses ($0.0\%$) on deceptive tasks.
- **Option B: The Capability Router (Valid but Incomplete)**
  - *Evaluation*: Sound and empirically validated by EXP-003, but too narrow. Limiting JEv to front-door routing ignores its massive utility in search, dialogue, and verification.
- **Option C: The Search Policy / Value Function in SET-CR (Strongly Supported)**
  - *Evaluation*: Highly effective. In SET-CR, JEv provides the heuristic $h(n)$ and branch policy $\pi(a \mid s)$, solving the exponential branching bottleneck without corrupting state.
- **Option D: The Verification / Stopping Layer (Partially Supported)**
  - *Evaluation*: Useful for semantic/perceptual checks, but must NOT override symbolic invariant checks ($S_{invariants}$).
- **Option E: General Decision Substrate Used at Multiple Points (WINNER / STRONGEST HYPOTHESIS)**
  - *Evaluation*: **The most defensible and unified architectural role**. JEv is not the entire brain; it is the **System 1 Decision Engine** called as a sub-routine across multiple stages:
    1. *Front-Door Triage & Speech Act Selection* (Stage 1 Communication)
    2. *Branch Expansion & Pruning in SET-CR* (Stages 3 & 4 Brainstorming & Planning)
    3. *Semantic Goal & Safety Verification* (Stage 6 Agentic Execution)
- **Option F: Narrow Routing Only (Rejected)**
  - *Evaluation*: Excessively timid. Fails to leverage the shared mathematical structure of decision problems across reasoning.

## 13. The Deeper Connection: Separating Generation, Decision, Execution, and State

Paartha’s previous research and this JEv audit converge on a singular foundational truth:

> **The primary failure of modern Artificial Intelligence is the conflation of Generation, Decision, Execution, Verification, and State into a single next-token probability distribution.**

Paartha's architecture enforces a clean, orthogonal separation of concerns:

```
  ┌────────────────────────────────────────────────────────────────────────┐
```

## 14. Stage-by-Stage Implications Across the Capability Ladder

1. **Stage 1 (Speak / Communicate)**:
   - JEv acts as the **Dialogue Manager**: decides speech acts (`DIRECT_ANSWER`, `CLARIFY`, `EXPLAIN`, `UNKNOWN`), while the surface realization engine verbalizes proof traces from $\mathcal{K}$.
2. **Stage 2 (Understand Complex Requests)**:
   - JEv classifies intent, identifies missing slots, and extracts semantic frames without generating prose.
3. **Stage 3 (Brainstorm / Generate Solutions)**:
   - JEv rapidly evaluates and ranks candidate hypotheses generated during divergent search.
4. **Stage 4 (Plan)**:
   - JEv acts as the heuristic evaluation function inside SET-CR, ordering dependency milestones.
5. **Stage 5 (Write and Understand Code)**:
   - JEv selects algorithmic templates, data structures, and library imports, leaving exact syntax synthesis to AST compilers.
6. **Stage 6 (Execute Agentic Tasks)**:
   - JEv performs instant tool dispatch, safety policy guardrails, and loop termination checks.
7. **Stage 7 (General Goal-Directed Problem Solving)**:
   - Full orchestration: JEv System 1 decisions provide the fast heuristic guidance for System 2 SET-CR autonomous scientific search.

## 15. Risks and Architectural Limitations

1. **The Discretization Trap**: If a problem cannot be cleanly bounded into $\le 255$ discrete options, a boolean, or an ordered scalar, JEv cannot evaluate it directly without prior candidate generation.
2. **Calibration Collapse Under Severe Distribution Shift**: While RLCD guarantees calibration on in-distribution decisions, EXP-009 proved that novel out-of-distribution shifts can fool learned confidence. Structural invariants must always remain the final arbiters of truth.
3. **Latency Accumulation in Deep Search**: While a single JEv call takes only 70–500ms, calling it 100 times in a deep search tree accumulates 10–50 seconds of latency unless search is aggressively pruned.

## 17. The Smallest Validating Experiment: EXP-JEV-0

To validate this architecture empirically without speculative engineering:

- **Experiment ID**: `EXP-JEV-0` (Calibrated Decision Substrate for Dialogue & Routing under Uncertainty).
- **Core Question**: Does separating decision (calibrated choice) from surface realization outperform an autoregressive LLM on intent routing, unknown detection, and communication calibration under ambiguous queries?
- **Experimental Conditions (5 Seeds Each)**:
  1. *Condition A (Monolithic LLM Baseline)*: A standard 8B autoregressive model prompted to perform joint classification, unknown detection, and response generation in one pass.
  2. *Condition B (Uncalibrated Fast Gate - SIP-001 Baseline)*: Paartha's existing runtime with output-entropy gating.
  3. *Condition C (Paartha + Calibrated Decision Substrate)*: Paartha v0 architecture with an explicit, calibrated classification head (or JEv API call) determining speech acts + missing information flags, followed by KRS-001 deduction and grounded verbalization.
- **Evaluation Metrics**:
  - **Decision Accuracy & Regret**: Percentage of correct speech act and capability dispatch decisions.
  - **Calibration Error (ECE / Brier Score)**: Correlation between reported confidence and empirical correctness.
  - **False Clarification Rate**: Rate of unnecessarily asking for clarification when facts are present.
  - **Hallucination Rate**: Frequency of fabricating unverified facts on missing-knowledge queries.
  - **End-to-End Latency and Compute Cost**.

## 18. What Should NOT Be Built Yet

To preserve research integrity and prevent wasted engineering:
1. **DO NOT train a custom 7B foundation decision model from scratch**. Paartha should initially test this principle using available calibrated decision models (e.g., Jev API / fine-tuned ModernBERT classifiers) before investing compute in pretraining a proprietary decision backbone.
2. **DO NOT replace SET-CR with pure decision models**. JEv is an action selector, not a replacement for state search and rollback.
3. **DO NOT abandon symbolic invariants ($S_{invariants}$)**. Statistical decisions must never be allowed to overwrite logical constraints.
4. **DO NOT write a custom DSL or complex attention engine**. Use standard machine-native interfaces (JSON / typed schemas).
